## Decisions and why

* **Production, Distribution (new), ReceiveStock stay full pages.** Line items or a multi-part job, per COMPONENTS.md. Production is a top-level tab, so no breadcrumb; the others are detail pages and keep theirs.
* **Purchasing new request is a drawer.** Four fields, no table, the list should stay in place.
* **Inflight record delivery stays a drawer.** Four fields plus context line.
* **Inventory count is a dialog.** One question per item (counted quantity and a reason). The item field only appears when it is not already known. This deliberately departs from the "3 to 5 fields means drawer" rule because the content is short and a full-height panel was mostly empty.
* **Approvals review stays a drawer.** It is a record with context (details, trail) plus a decision that needs a reason.
* **Primary buttons on full-page forms live in the form footer** (Save production, Send for approval, Confirm and add to stock), because the fields are on the same screen and a header button would sit a full scroll away from them. Lists keep the single primary in the header.
* **Confirmations avoided.** Approve, withdraw, remind and mark-read act at once and say what happened in a dismissable banner; nothing is confirmed twice.
* **Cross-screen consistency.** Purchase requests, dispatches, decisions, and received stock now travel through the same remembered state as Approvals and Notifications (keys `purchAdded`, `dispAdded`, `recv`, plus the existing `appr`, `apprActs`, `read`). Seed data was aligned (Approvals R-0211 is Chicken, R-0213 added; Purchasing R-0209 replaces R-0210).

## Not done or limited

* Production does not change Inventory (made goods and raw materials used are only shown on its own page). In-flight deliveries and stock counts are not remembered between screens.
* Receive stock opens only for requests the demo knows (R-0213, and R-0216 or R-0214 once approved).
* No new notifications are created when you raise something.
* `READ-ME.txt` still lists the older set of remembered items (outside this scope).
* Tables on Production (Made today), Inflight invoices fit on a phone; the other lists stack with page-local CSS (`.stk`). The same pattern should live in `app.css`.

## Shared changes wanted (not made, outside scope)

1. `app.css`: `.shell{align-content:flex-start}`. On a phone a short page (Receive stock, empty lists) shows a blank band of about 70px between the top strip and the content, because the wrapped flex lines stretch to the 800px minimum height.
2. `app.css`: `.tr` and `.th` are content-box, so the 52px minimum row becomes 65px. `box-sizing:border-box` would give the intended density; every table is affected.
3. `app.css`: promote the phone stacking pattern (`.stk`, cells marked `data-l`, `.c1` for the lead cell, `.ca` for actions) next to `m-wait` and friends; five screens here use a page-local copy.
4. `app.css`: focus ring for `textarea` and for programmatically focused groups (`.lbl[tabindex="-1"]`); currently added in each page's own style.
5. `app.css`: `.crumb` renders about 24px tall on these pages (below the 32px minimum control size). A `min-height:32px` that applies to links as well as buttons would fix it.
6. COMPONENTS.md: document "quiet row link" (`lnkb`) as the row action for follow-up navigation, and "primary in a full-page form sits in the form footer".
